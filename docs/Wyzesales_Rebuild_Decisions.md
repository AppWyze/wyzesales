# Wyzesales Rebuild — Decisions & Scope

A running record of what's been decided for the Flutter + Supabase + Netlify rebuild of Wyzesales, consolidated from the design discussion so far. Companion to `WyzesalesDailyLoad_Analysis.md`, `Wyzesales_Screens_and_Recommendations.md`, and `Wyzesales_Forecast_Redesign.md`.

---

## 1. Architecture

- **Stack**: Flutter (mobile, tablet, and desktop from one codebase) + Supabase (Postgres, Auth, Storage, Edge Functions, Cron) + Netlify (hosting the Flutter web build). Same stack as the existing SeaWyze app.
- **WyzeSalesExtract becomes a plain data extract.** It pulls raw facts and reference data from the WCSA IQRetail database via ODBC and loads them into Supabase — no aggregation, no business rules, no forecasting inside the .exe. This removes the need to involve WCSA's IT/security team for every future logic change.
- **All aggregation and business logic moves to Supabase**, split between:
  - **SQL views / materialized views** for stateless, single-pass logic: fiscal-year date math, the `ConsolidatedSales`-style rollups, the profit-percentage calculation, and the location-code remap (as a small reference table, not hardcoded IF/ELSEIF).
  - **Supabase Edge Functions** for stateful or multi-branch logic: the seasonal forecast (see Section 4) and any validation/alerting logic.
- **Business-rule configuration** (excluded customer accounts, the sales-rep override list, the supplier suppression list) moves into editable Supabase tables rather than a config file on the Windows server — changeable by Craig directly, no redeploy.
- **Multi-tenant from day one.** Even though only WCSA exists today, the schema carries a client/tenant identifier throughout, so adding another Wyzelink client later doesn't require a schema rework.
- **Data migration**: not needed, resolved 2026-08-21. WCSA's live database has more than 3 years of history, but it was a deliberate business decision early in Wyzesales' development to only ever look at the last 3 years — older data was agreed to be irrelevant and distorting. Since the daily-load pipeline (both the text-file extract and the Xojo database it feeds) has therefore never held more than that same rolling 3-year window at any point, there's no older data anywhere to recover. The first run of the rebuilt extractor against Supabase naturally reconstructs the same 3-year window the current app already shows — that first run *is* the migration, not a separate project. Budget figures (the one thing the daily extract never touches, so it couldn't have regenerated anyway) also need no migration: confirmed those are all still zero, since WCSA hasn't started using that feature yet.
- **Cutover plan**: run the new app in parallel with the current Wyzesales for a period, comparing numbers, before WCSA fully switches over — consistent with how carefully everything else in this project has been validated.

## 2. Bugs confirmed as fixes, not preserved quirks

- **Stale branch/location on Quotes and Sales Orders.** The current daily-load script never looks up the correct branch for these two files — every row silently inherits whatever branch was left over from the last Sales Analysis row processed. The rebuild resolves branch correctly and consistently for every dataset (Transaction, Sales Analysis, Quotes, Sales Orders alike), directly from each transaction line's own warehouse code (corrected 2026-08-21 — an earlier draft tried to derive it from the selling rep's "assigned branch" instead, which turned out not to exist anywhere in WCSA's actual data; see `Wyzesales_Schema_DesignNotes.md` Section 7).
- **Seasonal-forecast averaging bug.** The old forecast always checked one specific month (February) to decide whether to average against a prior year or not, regardless of which month was actually being forecast. Superseded entirely by the Holt-Winters redesign (Section 4), which doesn't have this failure mode.
- **Year 1/Year 2 profit swap on Sales Analysis and Sales by [Dimension]** (found while building the rollup views — see `Wyzesales_Rollups_DesignNotes.md` Section 2, not yet sanity-checked with you). `SalesAnalysisBuilder.cs` deliberately preserves a copy/paste bug from the original script: the profit figures shown for "Year 1" and "Year 2" belong to each other's periods (Year 3 and all value/quantity figures are unaffected). Treated the same as the two bugs above — fixed, not preserved, in `v_dimension_monthly_sales`. Worth comparing last year's/the year-before's profit numbers between old and new once you can, since they'll now differ from what you're used to seeing.

## 3. Sales rep attribution

WCSA's database already has two distinct facts for every sale: the rep recorded on the invoice itself, and the rep assigned to that customer in the debtor master. Today's system (already ported into WyzeSalesExtract) defaults to the invoice's rep, except for a hardcoded list of ~11 "override" accounts where the customer's assigned rep takes precedence instead.

**Decision**: preserve this behavior exactly, but generalize the mechanism —

- Every transaction stores **both** the invoice's rep and the customer's assigned rep as separate fields, not just for the override accounts.
- The override list becomes a flag on the customer record ("attribute this customer's sales to their assigned rep") — editable directly by Craig or WCSA staff, not a hardcoded array requiring a code change.
- **Row-level security (who can see a row)** uses a union rule: a user can see a transaction if their rep code matches *either* the invoice's rep or the customer's assigned rep — so nobody's own legitimate work is ever hidden from them.
- **Reporting/attribution (whose number it counts toward)** uses the single resolved value from the override rule above, feeding Dashboard, Performance, and Budget numbers.

## 4. Forecast redesign

Full detail in `Wyzesales_Forecast_Redesign.md`. Summary: replaces the old two-year seasonal-ratio comparison with **Holt-Winters triple exponential smoothing** — tracks level, trend, and seasonality separately, uses all available history with more weight on recent months. Three-tier confidence fallback based on how much history an entity has (24+ months = full method, 12–23 = partial, under 12 = simple trend projection, each tagged with a confidence level). Smoothing parameters and thresholds live in a Supabase settings table, tunable without a redeploy. Budget figures and forecast figures live in separate tables from the start, eliminating the old backup/restore dance entirely. To be validated via backtesting against real historical data before cutover.

## 5. User roles and access

Four tiers, confirmed from the current User Management screen:

| Role | Access |
|---|---|
| **User** | Own transactions only (per the union rule in Section 3) |
| **RegUser** | All transactions for their assigned branch/region |
| **AdminUser** | Full access to all WCSA data |
| **SuperUser** | Full access, plus exclusive access to the User Management screen — Craig only |

User accounts are created directly (Craig sets up the account and hands over login credentials out of band), and the user can change their own password after logging in — no self-service email invite flow needed.

**Budgets screens — Admin/SuperUser only (2026-08-21).** Craig asked that User/RegUser accounts not see the Budgets screens at all, not just be blocked from editing them. Implemented at the Flutter app layer, in two places: `app_shell.dart` hides the "Budgets" nav section entirely unless `profile.canEditBudgets` (adminuser/superuser); `budgets_screen.dart` itself now shows a plain access-denied message instead of the entity picker/grid for anyone else, which is the actual enforcement point — the nav gate alone wouldn't stop a direct/bookmarked URL to `/budgets/:dimension`, since the router has no role-based route guard. Deliberately left `budget_figures`' own RLS SELECT policy (schema/001, readable by any profile for the client) untouched, per Craig's explicit answer that the Performance screen's "R Target"/"% Target" figures — sourced from the same table via `v_dimension_performance` — should keep showing to everyone. That means this is a UI-layer restriction only: a User/RegUser can't reach Budgets through the app, but the database itself doesn't block them from querying `budget_figures` directly (e.g. via the Supabase REST API with their own token) the way it would if the RLS policy were tightened. Worth knowing, not currently seen as a problem since it matches what was asked.

Each user record carries: name, email, contact number, level (one of the four above), rep code, and branch code — matching the existing Add/Edit/Delete Users screen.

**Role model changed under multi-tenancy (2026-08-25) — see Section 9.** SuperUser as a distinct top tier is retired: schema/008's role migration moves Craig's own account (the only row that had it) to AdminUser, and every AdminUser can now add/edit/delete users, not just a single top-tier account — Craig's own decision, "essentially super user should fall away and be replaced with administer-platform... all adminuser's should be able to add, delete and edit users." Cross-tenant reach (seeing/managing every client, not just your own) is a separate flag entirely, `is_platform_admin`, covered in Section 9 — it's not a fifth role level, and it's orthogonal to AdminUser/RegUser/User. `superuser` stays in the `user_level` Postgres enum as an unused legacy value (can't be cleanly dropped without recreating the type) but nothing is assigned it going forward. The table above is otherwise unchanged — User/RegUser/AdminUser access rules are exactly as documented.

**Correction — `mounted` vs `context.mounted` is not one-size-fits-all (2026-08-25).** Craig's next `flutter analyze` came back with 9 issues: the same `use_build_context_synchronously` lint, but now firing on the very lines just "fixed" to `context.mounted` (3 in `platform_admin_screen.dart`, 5 in `settings_screen.dart`), plus a new `unnecessary_non_null_assertion` warning. The lint's own message spells out the actual rule, which is more precise than "always use `context.mounted`": *"Guard a `State.context` use with a `mounted` check on the State, and other BuildContext use with a `mounted` check on the BuildContext."* In other words it depends on what kind of `context` is being used at that call site:
  - Inside a `State` subclass's own method, where `context` resolves via the inherited `State.context` getter with no local `context` parameter shadowing it (e.g. a dialog's plain `_save()` method) — guard with the bare `mounted` (the State's own getter). This is what all the "fixed" spots above actually were, and why changing them to `context.mounted` introduced new findings instead of clearing them.
  - Where `context` is a distinct local variable or parameter — a nested builder callback's `context`, or a `BuildContext` passed explicitly into a plain (non-State) function/method, like `_UserRow._confirmDelete(BuildContext context, WidgetRef ref)` in `settings_screen.dart` — guard with `context.mounted` instead, since that `context` isn't tied to any State's own `mounted`.
  This also explains the original session's earlier fix correctly: those spots were nested `builder:` callbacks shadowing the outer `context`, which really did need `context.mounted`. The mistake this time was applying that same fix to a syntactically different case (a plain State method with no shadowing) without checking which case actually applied. Reverted all 8 flagged spots back to bare `mounted`, left the one genuinely-parameter `context` (`_confirmDelete`) on `context.mounted`, and removed the stray `license!` non-null assertion the warning also caught (Dart's flow analysis already treats `license` as promoted at that point once `atLimit` — itself gated on `license != null` — is true, confirmed by the analyzer directly). Verified via tree-sitter, pushed the corrected files, confirmed byte-identical via `md5sum`. Not yet re-confirmed by Craig's own `flutter analyze` — needed before this can be called done.

## 9. Multi-tenancy — licensing, platform admin, per-client support logins (2026-08-25)

Built per `Wyzesales_MultiTenancy_Design_Proposal.md`, reviewed and confirmed with Craig before any code was written (all 8 original questions plus one AskUserQuestion follow-up on platform-admin scope). Same shape as SeaWyze's Admin/Settings tier system, simplified throughout to WyzeSales' actual unit — **a client is users only, never vessels** — so every vessel-shaped field SeaWyze carries (`max_vessels`, `base_vessels`, `price_per_additional_vessel`, `helm_tier`) was dropped entirely rather than carried along unused.

**Schema — `schema/008_wyzesales_multitenancy.sql`:**
- New `pricing_plan` table (name, description, `base_price`, `price_per_additional_user`, `base_users`, currency, `is_active`) and `license` table (one per client — `max_users`, `base_users`, dates, status, `annual_price`, `discount_percent`).
- **`discount_percent` instead of a price-override flag** — Craig's own preference over my original `is_custom_price` suggestion: a manually negotiated rate is expressed as a percentage off the plan-derived total, so it stays correct automatically if the base plan's rates change later, rather than freezing a stale absolute number the way SeaWyze's own plan-recalculation silently does today (it overwrites every license's `annual_price` on a rate change, including hand-negotiated ones — see the design doc Section 1's write-up of that as a real gap, not copied here).
- `profiles` gains `is_active` (mirrors SeaWyze's deactivate-without-delete) and `is_platform_admin` (WyzeSales staff — Craig's account, plus each client's `support+<code>@wyzesales.com` login).
- Three `SECURITY DEFINER` helpers (`get_my_client_id()`, `is_adminuser()`, `is_platform_admin()`) — same recursion-safe pattern `005` established for `is_superuser()`, needed because RLS on `license`/`pricing_plan`/`clients` now has to query `profiles`, same as the original recursion trap.
- RLS on the two new tables is **tighter than SeaWyze's own equivalent**, deliberately: SeaWyze's `platform_admin_update_pricing`/`platform_admin_insert_license` policies are `USING(true)` — any authenticated request can write them, the `is_platform_admin` check exists only in the Flutter screen, not the policy. - **Seat limit enforced at the DB level**, not just in the app (Craig's decision 4) — a trigger on `profiles` insert/update checks the client's `license.max_users` against its active, non-platform-admin user count, and raises rather than silently allowing an over-limit signup. SeaWyze only checks this in its Flutter "Add user" flow, so a direct API call bypasses it there.
- **Role migration**: every row with `level = 'superuser'` (today, just Craig's own account) moves to `adminuser` + `is_platform_admin = true`. `profiles_superuser_all` (schema/005), which had no client scoping at all — a real cross-tenant hole once more than one client exists — is replaced with two narrower policies: an AdminUser can only manage their own client's users, and cross-tenant reach requires `is_platform_admin()`. `budget_figures_write`/`_update` narrowed from `level in ('adminuser','superuser')` to `adminuser` only.
- **WCSA backfill**: a `Standard` pricing_plan row and a license row for the existing WCSA client, so the app finds real data under the new model instead of nulls. Figures are explicit placeholders (`base_price` 2500, `price_per_additional_user` 350, `base_users` 5, `max_users` 20, all ZAR/month) — not a real quoted price, adjust via the new Platform Admin → Pricing/Licenses tabs immediately after deploying.
- **Not done by this migration, needs a manual step after it runs**: creating the `support+wcsa@wyzesales.com` login itself. Supabase Auth users can't be created from plain SQL (inserting into `auth.users` directly bypasses identity/credential setup and isn't supported) — create it via the new `create-user` Edge Function once deployed, or the Supabase dashboard, with `is_platform_admin = true` and `client_id` = WCSA's.

## 10. `sales_document_facts` primary key — Staging still on the pre-fix schema (2026-08-25)

While syncing docs into Craig's canonical `Desktop/Wyzesales/` folder, its copy of `001_wyzesales_foundation.sql` turned out to differ from the one in this project's own docs — missing a fix made to that file while WyzeSalesExtract was being built (see `001`'s own current comment on `sales_document_facts`): the primary key was originally the natural key `(client_id, document_kind, document, item_code)`, corrected to a plain generated `id` once it was clear a real document can legitimately carry the same item on two separate lines, which the natural key would silently collapse into one.

Production doesn't exist yet (Craig hasn't created it), so this is a Staging-only problem — a fresh Production just runs the already-corrected `001` and never sees the issue.

**Fix: `009_wyzesales_sales_document_facts_pk_fix.sql`** — adds a generated `id` column (Postgres backfills it for any existing rows automatically), drops the old natural-key primary key, adds the new one on `id`, and re-adds the `(client_id, document_kind, document)` index the corrected `001` expects. Written defensively (`IF EXISTS`/`IF NOT EXISTS`, plus a existence check before the final `ADD PRIMARY KEY`) so it's a no-op if run twice, or run against an environment that's already on the corrected schema. Craig still needs to run this against `wyzesales-staging` himself — not run yet as of this entry.

As a side effect, `sales_by_screen.dart`'s precomputed `momDelta`/`yoyDelta` maps (the raw-Rand deltas Section 15 added specifically for the old dropdown) are no longer used anywhere and were removed.

**Horizontal scrollbar.** `ResponsiveDataTable` now wraps its horizontal (and, where applicable, vertical) `SingleChildScrollView`s in a `Scrollbar(thumbVisibility: true, ...)` each with its own explicit `ScrollController` — a real, documented Flutter gotcha here: a `Scrollbar` with no controller attaches to whichever `Scrollable` notification reaches it first, which is ambiguous/wrong the moment there's more than one scrollable in the same subtree (as there now is, horizontal + vertical nested). Giving each `Scrollbar` its own controller, matched to its own `SingleChildScrollView`, is the standard fix and keeps the two independent.

**Even spacing, eliminating white space.** Root cause: Flutter's `DataTable`, like `Wrap` (Section 15's follow-up), always sizes itself to its own intrinsic column widths — the "fill the width" fix from Section 12 (`ConstrainedBox(minWidth: viewport width)`) made the *panel* full width but never stretched the *columns* into that space, leaving a blank gutter after the last column exactly like the KPI tiles did before their own fix. `DataTable` has no flex-column-width API to reach for instead, so `ResponsiveDataTable` now grows `columnSpacing` (the fixed gap `DataTable` puts between every pair of columns) until the table's own rendered width exactly matches the viewport — spreading the leftover space out as gaps rather than stretching any column's content, the same philosophy as every other "spread evenly" fix this session. Because Flutter can only report a `DataTable`'s natural width *after* laying it out once, this is a genuine two-pass widget: it lays out with default spacing, measures the real rendered width via a `GlobalKey`, and — if narrower than the viewport — immediately re-lays-out with the computed spacing. That means a one-frame "pop" from packed to spread is possible on load or on a window resize; there's no single-pass way around that for a widget with no built-in flex-width support. It only re-measures when the viewport width actually changes, not on every rebuild, so it settles immediately rather than oscillating.

### 18a. Branch filter not applying — the refetch trigger was a race, not a query bug (2026-08-26)

Craig, with 4 screenshots of Sales Analysis' Table tab: "It is not working. When I select a branch nothing is filtered but when I clear the filter then it filters." Selecting Branch = Durban left the table showing all 448 unfiltered rows (with the chip and the local dropdown both correctly showing "Durban" selected); clearing the filter back to "All" then showed 149 rows, all Durban — i.e. the fetch that should have run the moment Durban was selected only actually landed on screen one action later, after clearing.

**Root cause.** Every screen wired into the global filters (`document_analysis_view.dart`, the Dashboard, Sales by [Dimension], Performance, YTD Comparative, and Sales Analysis' own Graph tab) used the same hand-rolled trigger: compare `ref.watch(globalFiltersProvider)` against a `_lastFilters` field saved on the `State`, and if it changed, schedule the actual refetch via `WidgetsBinding.instance.addPostFrameCallback`. That extra frame of indirection is exactly where a second filter change (e.g. selecting Durban, then quickly clearing) can overtake the first — the callback scheduled for the first change can still be sitting in the queue by the time the second change's own `build()` has already run and moved `_lastFilters` on, so the refetch that finally executes doesn't line up with what's on screen at that moment. The query logic itself (`SalesRepository.fetchSalesDocuments`'s `.eq('branch_code', ...)` chain) was never the problem — it was always reading the current filter state correctly whenever it actually ran.

**The fix.** Replaced the `_lastFilters`-diff-plus-`addPostFrameCallback` pattern with Riverpod's own `ref.listen`, which exists specifically to run a side effect exactly once, immediately, whenever a watched provider's value changes — no extra frame, no hand-maintained "did it change" field to fall out of sync. Each of the 6 screens now does `ref.listen<GlobalFilters>(globalFiltersProvider, (previous, next) => _refetch());` (or the screen's equivalent reload method) directly in `build()`, and the `_lastFilters`/`_lastGlobalFilters` fields were removed entirely — nothing is left to race. `document_analysis_view.dart` and `performance_screen.dart` still separately call `ref.watch(globalFiltersProvider)` alongside the `ref.listen`, since those two also render the current filter values directly (dropdown selections); the other four don't need the value at all in `build()`, so the `ref.watch` there was dropped along with the field.

## 22. Server-side pagination for the line-level Document Analysis tables; Totals moved to the top app-wide (2026-08-27)

Craig, watching Sales Analysis' Table tab load 448 lines in one shot: "What happens when there a significant number of lines? e.g. Sales Analysis now has 448 lines. What happens when there 4000 lines? What is considered the norm in apps like this?"

**What was actually happening**: `SalesRepository.fetchSalesDocuments` fetched up to 1000 rows in a single query (newest first), with no pagination and nothing on screen indicating a filtered set past 1000 lines would silently lose everything older than the 1000th row. On top of the row cap, the table itself was Flutter's `DataTable`, which builds every row's widgets eagerly (unlike a lazily-built `ListView.builder`) — a genuine performance cost that scales directly with row count, independent of the 1000-row cap. Both the Document substring filter and the Totals row were computed client-side against whatever happened to already be in memory, which only ever worked because every row used to be fetched at once.

**The norm**, per the (already-delivered) explanation: real server-side pagination (a page at a time, not a single capped fetch), sorting pushed to the query rather than done client-side on a partial data set, a visible "Showing X of Y" indicator, and — separately — a Totals figure that reflects the true filtered result set regardless of pagination, the way Xero/QuickBooks-style report grids handle it. Craig confirmed: "This is what we need to do."

### 22a. Server-side pagination (schema/012)

Two new Postgres functions, additive only (no changes to `v_sales_documents` or any existing view/function):

- **`fn_sales_documents_page`** — one page of line-level rows (`LIMIT`/`OFFSET`, newest first), taking the same filter parameters `fetchSalesDocuments` already built from `GlobalFilters`, plus the `document` substring filter moved here from client-side. Returns the exact same column shape as `v_sales_documents`, so `SalesDocument.fromMap` needed no changes.
- **`fn_sales_documents_totals`** — `COUNT`/`SUM(quantity/value/profit)` over EVERY row matching those same filters, ignoring `LIMIT`/`OFFSET` entirely. This is the full-filtered-result-set aggregate the Totals row and the "Showing X-Y of Z" indicator are both sourced from.

Both are `language sql`, no `security definer` — same reasoning as schema/011's `fn_*_filtered` functions: they run as the calling role, so RLS on `sales_document_facts` still applies per-caller through `v_sales_documents` exactly as it does on a plain view query today.

`SalesRepository.fetchSalesDocuments` was replaced by `fetchSalesDocumentsPage` (one page, via `fn_sales_documents_page`) and `fetchSalesDocumentsTotals` (the aggregate, via `fn_sales_documents_totals`) — both called through `.rpc(name, params: {...})`, the same client-call shape already proven to compile in this exact file for schema/011's functions, rather than reaching for newer PostgREST client APIs (`.range()`/`.count()`) this codebase had never exercised before and couldn't verify against the real package here.

`document_analysis_view.dart` was rewritten around a fixed 100-row page size: `_pageFuture` (the current page, refetched on every page turn AND every filter change) and a separately-tracked `_totals`/`_totalsLoading`/`_totalsError` trio (refetched ONLY on a filter change, mirroring the Dashboard's existing `_dimensionData`/`_dimensionLoading`/`_dimensionError` pattern for exactly the same reason — a different refresh cadence than the main future) — so turning pages stays cheap instead of re-running the full aggregate query every click. A new `_PaginationBar` shows "Showing 1–100 of 4,238" with Previous/Next icon buttons, Next disabled once a page comes back short of a full page or (once the totals aggregate resolves) once the current page's last row would already be at or past the true total. A filter change resets back to page 0, since the page index the user was on may no longer exist against a narrower (or wider) result set.

**Column-header sorting on this one table is temporarily gone, not silently left broken.** The old sort re-ordered whatever page's rows happened to already be in memory — correct only because every row used to be fetched at once. With real pagination, sorting has to happen in the same query that produces the page (`ORDER BY` the requested column) to mean anything across pages; sorting just the visible page would quietly reintroduce the exact same "looks right, isn't" problem this whole change exists to fix. Safely parameterizing which column to sort by inside a plain `language sql` function needs either a fixed `CASE`-per-column expression or validated dynamic SQL — flagged as a real, separate follow-up rather than rushed into this migration. Rows are fixed to newest-first (`doc_date` descending), matching the SQL function's own `ORDER BY` and this table's original default order.

**Files changed**: `docs/schema/012_wyzesales_sales_documents_pagination.sql` (new), `data/repositories/sales_repository.dart` (`fetchSalesDocuments` replaced by `fetchSalesDocumentsPage`/`fetchSalesDocumentsTotals`), `data/models/sales_document.dart` (new `SalesDocumentTotals`), `shared/widgets/document_analysis_view.dart` (rewritten: pagination, server-side Document filter, `_PaginationBar`, column-sort removed from `_DocumentTable`, which is now a plain `StatelessWidget`).

### 23a. Column sorting (schema/013)

Section 22a deliberately left column-header sorting out of the paginated Document Analysis table, flagging it as "a real, separate follow-up" rather than an oversight — sorting a single page in memory only ever worked because every row used to be fetched at once, and doing it correctly once pagination is real needs the `ORDER BY` pushed into the query itself. This is that follow-up.

`fn_sales_documents_page` (schema/012) is rebuilt in schema/013 as `language plpgsql` with validated dynamic SQL, replacing the plain `language sql` version — a plain SQL function has no way to make `ORDER BY`'s target itself a bind parameter, and casting every sortable column to a common text key so a single `CASE` expression could pick between them would break numeric ordering (text-sorting "9" after "10"). The safe pattern instead: `p_sort_column` is matched against a fixed `CASE`/`WHEN` list of hardcoded column expressions — never the raw parameter itself — to build `v_sort_expr`, which is the only thing substituted into the query via `format()`'s `%s`; every actual filter value still goes through a genuine parameterized `USING` clause. There is no path from user input to a raw SQL fragment: `p_sort_column` can only ever select one of twelve fixed expressions, matching this table's twelve columns exactly (`document`, `document_kind`, `doc_date`, `sales_person`, `branch`, `category`, `item`, `customer`, `quantity`, `value`, `profit`, `profit_percent`) — "sales_person"/"branch"/"category"/"item"/"customer" sort by the same coalesced display name/code the table already shows in that column, not silently by a different underlying code.

Because Postgres treats a changed parameter list as a different function identity, schema/013 `drop`s the old 11-parameter `fn_sales_documents_page` before creating the new 13-parameter version (added `p_sort_column text default 'doc_date'`, `p_sort_ascending boolean default false`), rather than `create or replace` — this guarantees exactly one version of the function exists afterwards regardless of whether schema/012 was ever actually applied. `fn_sales_documents_totals` is untouched; an aggregate over the whole filtered set has no sort order to parameterize.

On the Flutter side, `SalesRepository.fetchSalesDocumentsPage` gained `sortColumn`/`sortAscending` parameters (defaults matching the SQL function's own defaults), and `document_analysis_view.dart`'s `_DocumentTable` is sortable again: a new `sortColumnKeys` list (index-aligned with its 12 `DataColumn`s, and with schema/013's `CASE`/`WHEN` list — the two must stay in step) maps a clicked column back to the key the RPC expects. Clicking a header now triggers a real re-fetch of page 0 under the new order, not a re-sort of whatever page is already on screen.

**Follow-up bug, same day, after Craig applied schema/013**: Sales Analysis' Table tab failed with `PostgrestException(... structure of query does not match function result type ... Returned type document_kind does not match expected type text in column 1.)`. This is the SAME enum-vs-text issue schema/012's header comment already flagged once (`document_kind` is a Postgres ENUM, not `text`) — but that first fix only ever touched the WHERE clause; the SELECT list itself had selected the bare, uncast `v.document_kind` since schema/012, while `returns table (document_kind text, ...)` declares that column `text`. This went unnoticed through both schema/012 (which never got far enough to run — its WHERE-clause bug was a parse-time error) and schema/013 (which fixed the WHERE clause but carried the SELECT-list bug over unchanged), only surfacing now that the function could finally execute for real. **schema/014** fixes it: `v.document_kind::text` in the SELECT list, matching what the WHERE clause and the sort CASE expression already did. ### 23c. Sticky headers and Totals — every table, not just the paginated ones

Flutter's stock `DataTable` has no native support for a frozen header row or a frozen "totals" row while the body scrolls — a real gap, not a small tweak. Two real ways to close it were put to Craig: a hand-rolled rewrite of `ResponsiveDataTable` (more work, but stays inside code this project can actually verify compiles, and fixes every table in the app at once) versus adopting a third-party package like `data_table_2` (less work, but a new dependency this sandbox has no way to check against — no pub.dev access, no local Flutter SDK — the same risk this project already steered away from once with `fl_chart`). Craig chose the hand-rolled rewrite.

`ResponsiveDataTable` no longer renders a single `DataTable` when it needs a sticky header. Instead it builds TWO `DataTable` instances from identical inputs (same `columns`, same `rows`, same `columnSpacing`, same fixed row heights) — which is what guarantees their column widths land pixel-identical without measuring or hard-coding any column width by hand, since `DataTable`'s column sizing is a pure function of those inputs. The first instance is clipped down to just the header (plus a caller-specified number of leading "pinned" rows — the Totals row, where a screen has one) and never scrolls. The second is the real scrolling body, shifted up by exactly the pinned block's height so its own copy of the header/pinned rows sits off-screen above the visible area, and clipped so that hidden copy is never visible or interactive. `headingRowHeight`/`dataRowMinHeight`/`dataRowMaxHeight` are now pinned to fixed values (matching `DataTable`'s own historical defaults) rather than left implicit, because the pixel math behind the split depends on knowing those heights exactly.

A new `pinnedRowCount` parameter tells `ResponsiveDataTable` how many leading rows to freeze — set to 1 on Document Analysis, Sales By, Performance, and YTD Comparative (all four have their Totals row as `rows[0]`, per Section 22b), 0 everywhere else (header-only sticky). **Budgets is the one exception**: its table cells are live `TextField`s each bound to a per-month `TextEditingController`, and the two-`DataTable` technique above requires mounting the same row content into two `DataTable`s at once — safe for plain `Text` cells, unsupported for a shared `TextEditingController` mounted into two `TextField`s simultaneously. Budgets passes a new `stickyHeader: false` flag and keeps its original single-`DataTable` rendering entirely unchanged; it does not get a frozen header from this change.

**Files changed**: `shared/widgets/responsive_data_table.dart` (rewritten: `stickyHeader` and `pinnedRowCount` params, two-`DataTable` pinned-header split), `shared/widgets/document_analysis_view.dart`, `features/dimension_templates/screens/sales_by_screen.dart`, `features/dimension_templates/screens/performance_screen.dart`, `features/ytd_comparative/screens/ytd_comparative_screen.dart` (all four pass `pinnedRowCount: 1`, or `1`/`0` conditionally on Performance where the Totals row itself is conditional), `features/dimension_templates/screens/budgets_screen.dart` (`stickyHeader: false`, otherwise untouched).

Craig confirmed the app was stable again on that revert.

**Second attempt, same day, after Craig confirmed the revert was stable.** Without a stack trace to diagnose against (this sandbox has no way to run Flutter), the most likely cause was reasoned out from the design itself: the hidden, permanently-clipped-away copy of the header — built into the scrolling body instance purely so its column widths match the visible pinned copy — still carried real `onSort` callbacks it could never actually be clicked through. `DataTable` only wraps a column header in a live, hoverable `InkWell`/`MouseRegion` when it has `onSort` set, so this meant two simultaneously-mounted sort-arrow regions for every sortable column, one of them invisible — the most plausible source of a `MouseTracker` assertion. The fix: `_buildTable` gained an `interactive` flag that strips `onSort` (and so the `InkWell`/`MouseRegion`) from that hidden copy entirely, plus the same hidden copy is now also wrapped in `IgnorePointer` as a second, low-cost layer of the same fix (it excludes that whole shifted-off-screen subtree from hit-testing without touching the ancestor `SingleChildScrollView` that actually captures scroll gestures). `stickyHeader` defaults back to `true`; this was Craig's explicit choice between retrying this targeted fix versus switching to the `data_table_2` package, having already seen one hand-rolled attempt fail on a real device.

**Third attempt, same day.** The `onSort`/`IgnorePointer` fix above stopped the `mouse_tracker` crash, but Craig immediately hit a second, DIFFERENT crash on the same screen — this time with a full stack trace to work from: `RenderConstrainedOverflowBox object was given an infinite size during layout`, pointing squarely at this file's `OverflowBox`es. Root cause: both left `minWidth`/`maxWidth` unset (meaning "inherit the incoming width constraint"), and the incoming width there is genuinely unbounded — this whole table sits inside the horizontally-scrolling `SingleChildScrollView` in `build()`, which deliberately gives its child unbounded width so a wide table can size itself past the viewport and scroll sideways. A bare `DataTable` tolerates that fine (it always reports its own finite intrinsic width regardless of how much space is "available"), but `OverflowBox`'s own reported size tracks the incoming constraint's max — an unbounded max made it try to BE infinitely wide, which a `RenderBox` may never do. Fix: both `OverflowBox`es now get an explicit `minWidth`/`maxWidth` of a newly-tracked `_tableWidth` — a concrete, finite number derived in `_scheduleMeasurement` (the larger of the table's natural width and the viewport width — the same number a bare `DataTable` would already have sized itself to at this point), falling back to the viewport width for the one frame before that measurement resolves.

### 23d. Switched to the `data_table_2` package

Craig asked directly: "What is the norm? How do other similar apps overcome this header/total issue?" The honest answer: production apps essentially never hand-roll a frozen header over raw table primitives — they use a purpose-built grid component that's already had this exact problem solved and tested against real devices (AG Grid and MUI's DataGrid are the equivalent choice on the web). Craig confirmed `data_table_2` has no cost (free, BSD-3-Clause, no paid tier) before choosing to switch rather than take a fourth blind swing at the hand-rolled version.

`data_table_2` is a documented in-place substitute for `DataTable`/`PaginatedDataTable` (its own README: "add '2' to the names of stock widgets... and that is it") — every existing `DataColumn` (including its `onSort` callback) and `DataRow`/`DataCell` across every screen is used completely unchanged; only `shared/widgets/responsive_data_table.dart` itself changed. `ResponsiveDataTable` now wraps `DataTable2` directly, keeping its exact prior public API (`columns`, `rows`, `sortColumnIndex`, `sortAscending`, `scrollsVertically`, `stickyHeader`, `pinnedRowCount`) so none of the five call sites (Document Analysis, Sales By, Performance, YTD Comparative, Budgets) needed to change at all. `pinnedRowCount`/`stickyHeader` now map onto `DataTable2`'s own native `fixedTopRows` (`fixedTopRows: stickyHeader ? 1 + pinnedRowCount : 0` — `fixedTopRows` counts the header itself, so its own default of `1` already matches this widget's old "always at least the header" baseline) instead of this file's own deleted clip/transform mechanism — the actual pinning behavior is now `data_table_2`'s, battle-tested by its own users, not a mechanism unique to this codebase that only Craig's device could ever actually exercise.

The other thing this deletes: the old two-pass `GlobalKey`-based width measurement that grew `columnSpacing` to eliminate blank space after the last column (Section 17's original fix). `data_table_2` already spreads plain `DataColumn`s evenly across the available width on its own — no measurement needed for that anymore. What's still needed is a floor under that stretching, so a many-column table on a narrow window doesn't just keep squeezing every column thinner instead of switching to horizontal scroll (the original, explicit ask). `ResponsiveDataTable._minWidth` supplies that floor as a plain, static estimate per column (based on its label's text length — "Sales Person" gets more room than "Qty" — clamped to a sane range), fed into `DataTable2.minWidth`. This is deliberately rough, deliberately not a runtime measurement of anything, and has no `GlobalKey`/render-tree dependency to get wrong — if a table looks too tight or too loose once Craig sees it, that's a quick, low-risk visual tweak, nothing like the three render-tree crashes the previous approach produced.

Budgets keeps `stickyHeader: false`, but the REASON changed: the old reason (mounting the same `TextField`-bound row content into two simultaneously-live `DataTable`s at once was unsafe) no longer applies — `data_table_2` renders the row list once, not twice, so that specific hazard is gone. Budgets stays unpinned because its Totals row deliberately stays at the bottom (Section 22b: Budgets was never included in the "Totals to the top" scope), not because of any remaining technical constraint — a frozen header alone would be safe to add there today if Craig ever wants it, flagged as an easy follow-up rather than applied unasked.

New repository method: `SalesRepository.fetchDocumentCounts` (`data/repositories/sales_repository.dart`), returning a `Map<String, int>` keyed by document_kind, defaulting every requested kind to 0 (a kind with zero matching documents gets no row back at all from a plain SQL `group by`, which is expected right at the start of a new month).

**The other 3 new metrics needed no new SQL** — all built from existing repository methods:
- **Top 5 Customer Concentration**: `fetchDimensionMonthlySales(dimension: customer, ...)`, same call `_loadDimension`'s own breakdown already makes, just fetched independently of whichever dimension the breakdown picker currently shows. Top-5-by-value sum ÷ total-of-all-customers sum, for MTD and for the whole fiscal year to date.
- **Rep Target Attainment**: `fetchBudget(dimension: 'sales_person')` (the true rep roster + targets, since a rep with a target but zero sales in a month has no row in `v_dimension_performance` at all — that view is generated FROM the sales rollup, so it would silently under-count the "of N reps" denominator) cross-referenced against `fetchDimensionMonthlySales(dimension: sales_person, ...)` for actuals. - **Gross Profit Margin** and **Revenue Target Attainment**: both fall straight out of data the KPI row already fetched (`salesMtd`/`profitMtd`/`salesYtd`/`profitYtd`, and a new whole-company Actual-vs-Target fetch shared with the chart below via a new `_fetchWholeCompanyTarget` helper — called twice per load/refresh on purpose, once for the KPI tile and once for the chart's own independent `AsyncSection`, trading one small extra query for not restructuring two already-working, independently-timed loaders).

**How MTD metrics behave at the start of a new month** (Craig asked directly): there's no special-cased "new month" logic anywhere, old or new — every MTD figure is just "sum of whatever's landed in `v_consolidated_sales`/the rollup views for the current calendar month, as of right now," the same way Sales MTD/GP MTD always worked. At 00:01 on the 1st, MTD is naturally small or zero and climbs through the day/month as the nightly extract lands real transactions — nothing resets or waits. The one thing that needed real handling: the four new metrics are ratios, and a ratio's denominator can genuinely be zero early in a month (no quotes raised yet, no sales yet). Added `ratioPercent()` to `core/utils/formatters.dart` — `numerator / denominator * 100`, returns `null` on a zero/missing denominator, same "let the UI render '—'" convention `variancePercent()` already established — so every new ratio tile shows "—" instead of a misleading 0% or a crash for the first little while of a month, then reports real numbers as soon as data exists. ## 30. Dashboard KPI tiles — Wrap replaced with a fixed 3x2 / 2x3 grid (2026-08-28)

**Why the old `Wrap` produced an uneven split.** `Wrap` fits as many fixed-width tiles as the available width allows onto a line before starting a new one — with 6 tiles at a fixed width, the resulting split (5+1, 4+2, 6, ...) was purely a function of whatever the window's current width happened to be, not a deliberate layout choice. Since there are exactly 6 tiles and `columns` is always 3 or 2, that's always exactly 2 or 3 full rows — never a stray leftover. Each tile stretches to fill an equal share of its row's width via `Expanded` (wrapping a `SizedBox(height: _kpiTileHeight)` to keep the height fixed while the width flexes), rather than sitting at the old fixed 180px — that's what fills a wide monitor properly instead of leaving whitespace down the sides, and what lets a tile shrink gracefully on a narrower window instead of forcing a width that might not fit. `_kpiTileWidth` is gone entirely; only `_kpiTileHeight` (still 150, per Section 29) remains fixed.

**The breakpoint.** `_kpiGridBreakpoint = 900` — 3 columns above it, 2 columns at or below it. First attempt just bounced back to `/login` (the allow-list entry hadn't been added yet at that point — expected, see Section 40's own note on this). Second attempt, after adding it, crashed with a red Flutter error screen: `Assertion failed ... uri.path.startsWith(newMatchedLocation) is not true`, thrown from inside go_router's own route-matching code.

**Root cause: Flutter web's default hash-based URL strategy collides with exactly what Supabase puts in the URL.** Without an explicit `usePathUrlStrategy()` call — which this app never had, an oversight from Section 40's own build, not something Craig did wrong — Flutter web routes off the URL's `#fragment` (`https://mysite.com/#/reset-password` is the shape it expects), leaving the actual path before the `#` irrelevant to the router. Supabase's recovery link puts its own token in exactly that same fragment (`.../reset-password#access_token=...&type=recovery`). The two collided head-on: go_router tried to parse Supabase's raw token string itself as if it were an app route, and its internal assertion caught the resulting nonsense location before it could do anything worse.

**Fixed by switching the whole app to real path-based URLs.** `usePathUrlStrategy()` (from `flutter_web_plugins`, a package that ships with the Flutter SDK itself — like `flutter_test`, not a pub.dev dependency, so unlike `csv`/`pdf`/`file_saver` there's no version to guess at here) now runs in `main.dart` before `Supabase.initialize()`. This makes go_router read its own location from the URL's actual path (`/reset-password`) and leaves the `#fragment` entirely to Supabase, resolving the collision at its root rather than working around it. `ResetPasswordScreen`'s own `Uri.base.fragment` check (for a used-up/expired link) is unaffected — that reads the browser's real URL directly, regardless of which strategy Flutter's router uses.

**One companion change this made necessary.** Under the old hash strategy, Netlify only ever needed to serve `/` — every route lived after a `#`, which browsers never send to a server, so the app's own router handled everything client-side no matter what. Under path-based routing, a direct load of any *other* route is now a real HTTP request for that literal path — clicking the password-reset link and landing straight on `/reset-password` is the immediate case, but this now applies to every screen (bookmarking `/sales-analysis`, or refreshing the browser while on `/settings`) — and without a server-side rewrite, Netlify would 404 all of them: there's no real file at `build/web/reset-password`, only `build/web/index.html`. Added `web/_redirects` (`/*  /index.html  200`) so Netlify serves `index.html` for every path and lets Flutter's router take it from there. This only matters once WyzeSales is actually deployed to Netlify — testing locally via `flutter run -d chrome`, Flutter's own dev server already falls back to `index.html` for any path regardless, which is why the crash was reachable locally at all before this file existed.

**Files changed**: `pubspec.yaml` (added `flutter_web_plugins`, an SDK package), `lib/main.dart` (`usePathUrlStrategy()` call added before `Supabase.initialize()`), `web/_redirects` (new file — Netlify SPA fallback).

**Built as schema/018**, three small `security definer` helper functions (`fn_customer_visible_to_rep` — the exact same union rule as `sales_document_facts_select`'s own 'user' branch, factored out; `fn_rep_sold_at_branch` / `fn_customer_sold_at_branch` — the branch/region analogue for RegUser), then five rewritten SELECT policies: `budget_figures_select`/`sales_forecast_select` (dimension-aware: Sales Person/Customer/Branch scoped per the rules above, Item/Category/Company hidden for User/RegUser), and `customers_select`/`sales_reps_select`/`branches_select` (scoped the same way; `items`/`categories` deliberately left open — same "no natural owner" reasoning). Every existing schema/006 policy being replaced had to be explicitly dropped first, not just added alongside — Postgres OR's every applicable policy together, so leaving the old "any client member" policy in place would have silently kept everything visible regardless of the new one.

**A subtle bug caught and fixed before it could ever ship**: making `customers_select` read `sales_document_facts` (to decide a User/RegUser's visibility) creates a two-way dependency, since `sales_document_facts_select` already reads `customers` (to look up `assigned_rep_code` for its own union rule). That's structurally the exact same class of bug schema/005 documents in detail — "infinite recursion detected in policy for relation X" — just a two-table cycle instead of `profiles` referencing itself directly. Fixed the same way schema/005 did: all three new helper functions are `security definer` with a pinned `search_path`, so their internal queries bypass the target table's own RLS instead of re-triggering it. Verified this doesn't just avoid an error but stays *correct*: `fn_customer_visible_to_rep`'s predicate is an exact mirror of `sales_document_facts_select`'s own union-rule subquery, so the customer row that subquery needs to look up remains visible under the new `customers_select` policy in exactly the cases where it needs to be.

**Mandatory Rep code/Branch code**: `_AddUserDialog` and `_EditUserDialog` (settings_screen.dart) both gained a `_repBranchRequired` check — Save is blocked with an inline error whenever Level is User or RegUser and either field is empty, and the field labels themselves switch from "(optional)" to a required `*` live as the Level dropdown changes. Deliberately does NOT also scope User-level access by Branch code, even though it's now mandatory alongside Rep code — `sales_document_facts_select`'s existing 'user' rule was never based on branch_code (a rep can legitimately sell across more than one branch), and extending that now would invent a new restriction Craig didn't ask for.

**One side effect worth Craig watching for, not a bug**: the Dashboard's Rep Target Attainment section currently fetches every sales person's budget figures in one call with no per-user restriction — after this migration, a non-admin viewing that section will only see figures for reps schema/018's rules make visible to them (their own row for User, their branch's reps for RegUser), which is the intended new behavior, but will look different from what a non-admin sees today.

## 47. Section 46's real-account test — a false alarm, a genuine Supabase login incident, and a re-confirmed design decision (2026-09-01)

Craig tested Section 46 by pointing his own `profiles` row at `level='user', rep_code='R01', branch_code='CPT'` and signing in. Sales Order Analysis, Quote Analysis, and a Sales-by-Sales-Person comparative table all showed rows for other reps (Johan Botha, R02, R03, R04, R05, "44") across multiple branches — "Doesn't seem correct." Since `sales_document_facts_select` (schema/001) had just been relied on as "already fully built and working" to justify not touching it in schema/018, this needed a real answer, not an assumption.

**Code audit first, before asking Craig to touch anything**: re-read `sales_document_facts_select` itself, confirmed no later migration ever adds a second, more permissive SELECT policy on the same table (Postgres OR's every applicable policy together, so a stray permissive one would silently win), confirmed every screen in question reads through a chain of `security_invoker = true` views/plain SQL functions with no `security definer` anywhere in that chain, and confirmed the Flutter app is built with the anon/publishable key, never `service_role`. Everything on the code side came back clean, which meant the gap had to be either in what's actually deployed, or in the live database itself.

**Getting there took most of the session.** Confirming what's actually live needed two things from Craig: `select relrowsecurity from pg_class where relname = 'sales_document_facts'` (true) and `select policyname, cmd, qual from pg_policies where tablename = 'sales_document_facts'` — but the second one coincided with Craig getting logged out of the Supabase dashboard entirely, `auth.supabase.io` stuck in an infinite redirect loop back to GitHub OAuth, surviving cookie clears, incognito, and a full machine restart. Root cause turned out to be a stuck GitHub OAuth grant — revoking Supabase's access at github.com/settings/applications and re-authorizing fresh cleared it. Separately, and confirmed via Supabase's own status page mid-incident, there was also a live, unrelated Supabase-side incident ("401 errors due to JWT rejections," Aug 28–29) that plausibly explains the "JWT access denied" error Craig saw right as he got locked out — a genuine coincidence of two problems landing in the same hour, not something either side of this project caused.

**Once back in, the actual policy text came back byte-for-byte correct** — exactly the `adminuser`/`reguser`/`user`-union logic schema/001 describes, ruling out "never deployed" or "silently overwritten" as the cause.

**The decisive test**: rather than keep debugging through the app/browser, ran the RLS check directly against the database — impersonating Craig's exact `auth.uid()` via `set_config('request.jwt.claims', ...)` + `set local role authenticated` inside a rolled-back transaction, then querying `sales_document_facts` directly. This matters because the Supabase SQL Editor normally runs as a superuser, which bypasses RLS entirely regardless of policy — a plain query there proves nothing about whether RLS actually restricts anything. The impersonated query came back with 715 total rows (not the full company's ~2,300+), split as `R01: 523, 44: 52, R03: 39, R05: 39, R02: 33, R04: 29` — genuine proof RLS *is* restricting R01's access; this was never a leak of unrestricted company-wide data.

**Why other reps' codes still legitimately appear**: two independent rules, easy to conflate. Who can *see* a row is `sales_document_facts_select`'s union rule (own invoices, or any row on a customer assigned to you, regardless of who actually processed it — Section 3's own reasoning: a rep's legitimate work is never hidden from them). Who gets *reporting credit* for a row is a separate function, `resolved_rep_code()` (schema/001): if a customer is flagged `attribute_to_assigned_rep`, that customer's sales always display under the assigned rep's code in the Sales Person column, regardless of who invoiced it. So a row R01 is fully entitled to see (their own invoice, or their own assigned customer) can still show a colleague's code in that column, because that's genuinely who the sale counts toward. Branch spanning DBN/JHB/CPT in the same screenshots is likewise expected, not a bug — the `user` level was only ever scoped by rep code, never by branch (only `reguser` is branch-scoped).
